# 生命周期与失败语义

## 状态机

```prodoc-flow
graph LR
  New[已注册] -->|mount| Mounted[已挂载]
  Mounted -->|unmount| Unmounted[已卸下]
  Unmounted -->|mount| Mounted
  Mounted -->|依赖消失 + reconcile| Pending[待挂载 / pending]
  Pending -->|依赖回来 + reconcile| Mounted
  Mounted -->|mount 失败| Failed[失败]
```

进程外模块还有一层**进程**状态（与上面的"挂载状态"正交）：

| `state` | 含义 |
|---|---|
| `pending` | 进程在起，还没握手完 |
| `ready` | 握手成功、贡献已注册 |
| `draining` | 收到排空指令，等模块退出（未应答调用按代结算） |
| `stopped` | 正常退出 |
| `failed` | 崩溃/启动失败（按 backoff 重试，超过熔断次数后停） |

`enabled = true` 而 `state = failed` 是"配置开着、进程起不来"，和"用户关掉了"
是两件事，宿主必须能分开显示。

## 失败语义一览

| 失败 | 结果 | 会不会自动恢复 |
|---|---|---|
| 依赖缺失 | 拒绝挂载，`pending` 记下缺的键 | 会（`reconcile`，依赖到位即挂） |
| `mount` 闭包返回 `Err` | 挂载失败，**不进 pending** | 不会（这是模块自己的 bug，自动重试会变成静默失败循环） |
| 子进程启动失败 | backoff 重试，200ms×2 上限 2s，5 次后熔断 | 有限次 |
| 子进程崩溃 | 同上，已就绪的贡献会失效、重连后重建 | 有限次 |
| 调用超时 | 该次调用失败，模块不受影响 | — |
| 事件投递返回 `Err` | 计数，不卸载 | — |
| 事件投递重入 | 内层丢弃 + 记一次失败 | — |

## 两处刻意的"不自动恢复"

**挂载闭包报错不进 pending。** 缺依赖是"还没轮到"，闭包报错是"它自己坏了"。
把后者也塞进 pending，就会变成每来一次服务变动就重试一次失败模块——错误被
重试掩盖，日志变成刷屏。

**事件投递失败不卸载模块。** 事件是观察通道。一个模块对某条通知处理不了，
不该因此丢掉它已经挂载的所有能力。

## 热替换（进程外）

```rust
handle.upgrade(new_config, timeout).await?;
```

顺序是：新进程起来 → 握手 `Ready` → **原子切流量** → 老进程 `Drain` → 退出。
新进程没就绪就不切（失败保老，可回滚）。这条路径同时被"配置代际"验证覆盖——
替换后调用打到的是新实例。

### 在途调用的结算（按连接代际）

每条连接有一个单调递增的代际（`generation`）。在途调用登记时记住自己所在的
代际，生命周期收尾时按代际结算：

| 事件 | 结果 |
|---|---|
| 连接排空 / 可逆停止 | 该代际上未应答的调用 → `Error{code:"drained"}` |
| 热替换换下旧实例 | 旧代际上未应答的调用 → `Error{code:"replaced"}` |
| 连接丢失 / 崩溃 | 该代际上未应答的调用 → `Error{code:"module_crashed"}` |

只结算**登记代际 ≤ 被关闭连接代际**的调用：热替换后新实例上的调用不会被误伤。
结算发生在连接 `shutdown` 之后（此时不可能再有结果回来），因此调用方不必等
各自的默认超时（600s）。

调用方主动放弃等待（丢弃 `invoke` 返回的 future）会撤销在途登记，不泄漏
pending；`ModuleHandle::in_flight_calls()` 可用于观测。

### 停止是有界的（端到端）

「排空」不是一个 `Drain` 帧就完事：一个不读 stdin 的模块能让宿主的每一次写
都阻塞在管道上。所以三条路径共享同一个预算，且**每一步都算在里面**：

- `invoke` 的 `ctx.deadline_ms` 覆盖「把 `Invoke` 写进连接 + 等 `InvokeResult`」；
- `drain(d)` / `stop(d)` 的 `d` 覆盖「发 `Drain` + 等模块退出 + `shutdown`」；
- `shutdown` 自己：取写锁有上限，拿不到（有 `send` 卡在管道上）或写方向留着
  半帧就**强杀**子进程，然后有界收尸；不会「超时就丢掉 future」把进程和锁都留着。

因此 `drain` / `stop` 返回 `Err(Timeout)` 的含义是**「没能优雅关停，已强杀」**，
而不是「我不管了」。句柄侧还有一层 `deadline + 2s` 的兜底，监督任务自身出故障
时调用方也不会挂住。

## 卸载顺序

1. 该模块名下的**子作用域先卸载**（递归，子先于父）——否则父的服务表先撤，
   子模块的 `unmount` 可能还要用父的服务；
2. 该模块 `mount` 返回的 `Disposer` **逆序**撤销；
3. `Module::unmount()`（disposer 之外的清理：关文件、停线程）。

第 3 步在 v0.6 之前**从未被调用过**——注册表撤完 disposer 就返回了。这是一个
典型的"接口存在但没人调"的死代码，已修。
