# 边界与纪律

这个仓库的价值一半来自"能做什么"，另一半来自**明确不做什么**——后者由门禁
测试守着，而不是靠自觉。

## 一、零领域依赖

**全部**框架 crate 都不许依赖任何应用 crate，生产代码里也不许出现应用领域词汇
（工具、技能、会话、人格、代理……这类只有某个具体应用才有意义的词）。

`crates/framework-gates` 有两条门禁：`Cargo.toml` 依赖表里没有指向宿主的项；
生产代码（`src/` 下，除 `bin/` 与 `tests.rs`）逐行扫描禁用词表。这是"这套框架
能被别的项目用"的**可执行证明**——一旦有人为了方便在框架里 `use` 宿主的类型或
新增业务分类，门禁立刻红。

覆盖范围包括协议 crate。它们曾长期被排除（理由是"协议表面尚未收敛"，而那正是
业务类型能长进来的原因），代价与收口过程见下文 §三。

### 为什么这么严

**反例**：v0.2 时 `MountContext` 里有两个字段 `tools` / `skills`，各配一个
`ModuleToolSink` / `ModuleSkillSink` trait，"给未来的工具模块预留接缝"。
审计发现：全仓 `mount` 闭包都是 `|_ctx| Ok(vec![])`、`register_tool` 零调用点、
`SkillSink` 从未实例化。**预留的接缝一次都没用过，却把两个业务词汇写进了框架**。
v0.3 删除。

教训：**给未来的预留，几乎总是错的**。真正需要时会加，那时也知道该长什么样。

## 二、零全局态

框架**不导出**进程级单例表。想表达"这个宿主里只有一份"，用 `Ctx`：它是显式
注入的，可以有任意多份、互不干扰。

原 `echo-context::kernel`（`TypeId` 键控的全局单例表）在 v0.3 搬到了宿主侧。
原因很具体：框架导出全局态，就等于宣称"一个进程只能有一套宿主"——而那正好
破坏了"这框架能被任何 Rust 应用使用"这个复用前提。

## 三、名字 + 存在性，而不是类型

框架只认**名字**与**存在性**：服务键、模块 id、事件名、作用域父链，四处都是
名字；协议里的贡献分类也只是一组与业务无关的形状。它从不要求跨模块的 Rust 类型，
也从不认识某一类业务概念。

这不是省事，是**可独立替换**的前提：要求类型 → 模块之间就得互相 `use`，换掉
一个要重新编译所有引用它的模块；认识业务分类 → 框架就得跟着某个应用的领域模型
一起演进。

### 落地一：服务表（`Ctx`）

注册时给名字与类型，解析时按**名字 + 精确类型**取，类型不符等于没找到。名字是
字符串，所以模块之间不需要共享任何类型定义。

三个直接后果：

| 后果 | 是缺陷还是选择 |
|---|---|
| 拼错的服务键只在运行期报错 | 选择。补偿是错误里带 `available` 全量清单 |
| 事件载荷是自由 JSON，没有 schema 校验 | 选择。schema 是宿主与模块的契约 |
| 模块之间不能直接调用彼此的 Rust 方法 | 选择。能调就不再有"可独立替换" |

### 落地二：协议（`Contribution`）

协议是同一原则的另一处落点——它承载的是**名字与形状**，不是类型，更不是业务
分类。贡献分类只有与业务无关的形状，外加一个**逃生口**：

| 变体 | 形状 |
|---|---|
| `Service` | 键 + 版本 |
| `Events` | 事件名清单 |
| `Command` | 名字 + 说明 |
| `Text` | 键 + 标题 + 顺序 |
| `Custom` | **宿主自定义**的 `custom_kind` + `name` + `payload` |

`Custom` 是业务词汇的唯一入口：`kind` 是宿主自己的词（`"report_generator"` /
`"chat_adapter"` / 任何字符串），`payload` 的形状由宿主与模块自行约定，框架只
搬运、不解释、不校验。于是**任何宿主想加一类贡献，写 `Custom` 就行，协议不需要
改**——"框架为每个业务概念加一个枚举变体"这条路被结构性堵死了。

线上标签是 `custom`，分类字段叫 `custom_kind`：载荷字段不能叫 `kind`，枚举 tag
已经占了那个名字，重复键会让整帧解析失败（`Service` 变体踩过这个坑，现在由
`custom_contribution_carries_host_defined_shape` 钉住）。

### 它怎么被强制执行：一次真实的清理

这条边界不是靠自觉守着的。2026-11 的审计把 `document/crates.md` 里那句"协议
表面尚未收敛，等 2 个以上真实外部使用者再动"落成了事实，结论比预期直接。

| 曾经的领域分类 | 在本仓 | 在 EchoAgentCore | 真实生产者/消费者 |
|---|---|---|---|
| 工具声明 | 仅测试 + conformance 夹具 | **无** | 0 |
| 技能目录 | 仅测试 | **无** | 0 |
| 模块实例（含能力位） | 仅 SDK 的实例模块 trait | **无** | 0 |
| 聊天寻址 / 入站消息 | 仅一条 serde 往返测试 | **无**（用自己的副本） | 0 |

关键事实：**EchoAgentCore 已经不依赖本仓**——它用自己仓库内的 `echo-context`
副本。所以那个"等 2 个以上真实外部使用者"的门槛，前提根本不成立：不是"还没人
用"，是"催生它的那个宿主也不用"。

于是四步收口：

1. **删掉**三个聊天平台类型（出站寻址、私聊/群聊通道、入站消息，共 63 行）——
   从来没有任何生产者构造过它们。
2. **把三个领域贡献变体换成 `Contribution::Custom`**（见上），并把"哪些贡献
   参与寻址"收进 `Contribution::target_name()` 放在变体旁边——否则每个调用方
   都得 match 一遍具体变体，被迫认识它本不关心的分类。
3. **门禁不再排除** `echo-module-api` / `echo-module-sdk`。此前这两个 crate 被
   排除在领域词审计之外，而那正是业务类型能长进来的原因。现在改为
   `KNOWN_DOMAIN_RESIDUE` 白名单，**且当前为空**。
4. 加一条**防腐烂**测试：白名单条目一旦不再触发违规就报错，逼着同步删除——白
   名单的天然倾向是单向变厚，没有这条它迟早变成"整个文件都豁免"。

排除整个 crate 与白名单的差别很实际：

| 做法 | 新增领域词 | 删掉残留后 |
|---|---|---|
| 排除 crate | 静默通过 | 无人知道白名单该更新 |
| 白名单 | **测试红** | **测试红，要求删条目** |

### 为什么"等以后"不是个选项

原计划是"等有第二个真实使用者再评估"。这次的结论是：**那个"以后"不会自己
到来**。一边是零使用者、一边是持续维护一个会误导人的协议表面——等待不产生任何
信息，只产生新的业务类型，而后来者看到"协议里还有业务类型"，会以为那是允许的。

这与本页 §一里那个预留接缝（`ModuleToolSink` / `ModuleSkillSink`）的教训是同
一条：**给未来的预留，几乎总是错的**。

### 如果一定要类型

正确做法是在宿主侧做适配层：把它从 `Contribution::Custom` 的 `payload` 翻译成
自己的 trait 对象。**适配层可以认识业务，框架不行。**

## 四、不做的三件事

**不锁语言。** 协议是 JSON 帧，不是 Rust ABI。所以有了纯 Python 模块示例与
它的 3 项测试；也所以框架不能要求"模块必须实现某个 trait"。

**不做权限模型。** 进程外能靠 `env_clear` + `rlimit` 做隔离（这是**资源**
隔离，不是权限），进程内则假定模块可信。完整的 capabilities 声明与宿主中介
（fs / net / proc）没有做——它是"不可信第三方模块"这个场景才需要的，而那需要
先有 wasm 沙箱轨。

**不做业务持久化。** 模块状态存哪、格式怎么迁移，是模块与宿主的事。框架只提供
"注册可撤销"这一条纪律。

## 五、判定"这段代码该不该进框架"

三个问题，任一为"是"就不该进：

1. **它换了个应用还成立吗？** —— "工具调用"不成立，"按名字找服务"成立。
2. **删掉它，机制还完整吗？** —— 预留的未来接缝 → 删（见上面的反例）。
3. **它要求框架认识某个具体类型吗？** —— 是就下沉到宿主侧适配层。

## 六、当前已知的边界

| 边界 | 状态 |
|---|---|
| `dylib` 轨 | 未实现（Rust 无稳定 ABI；若做优先评估 `stabby`） |
| `wasm` 轨 | 未实现（沙箱需求明确后再评估 wasmtime / extism） |
| 声明式注入的类型化 | 不做（见 §三） |
| 协议的领域分类 | **已清零**（见 §三）：领域宿主走 `Contribution::Custom`，框架不认识具体词汇 |
| 就绪等待 vs 立即失败 | 两种都有：`mount` 立即校验，`mount_when_ready` 等待 |
| 状态迁移协议（`export_state` / `import_state`） | 未实现（可选） |
| 多模块共享预算 | 未实现（`rlimit` 管单个模块失控；cgroup 级共享未做，收益/成本不划算） |
